# Compiler model

Valence parses JavaScript and TypeScript modules in the Vite client graph. A function-level `'use main'` directive moves that async function's implementation into Electron's main bundle and replaces its renderer body with an asynchronous call. A top-level `'use main'` directive marks supported exported functions in the module.

## Boundary rules

- Main functions must be asynchronous. Renderer callers receive a Promise.
- Functions cannot close over local variables, component state, props, or other lexical bindings. Pass required values as parameters.
- Arguments and return values use Electron structured clone. Values such as `Date`, `Map`, `Set`, `ArrayBuffer`, and cyclic object graphs are supported. Electron objects, functions, symbols, promises, and weak collections cannot cross the boundary.
- Value imports referenced by a main function are retained in the main bundle and pruned from the renderer when unused there. Type-only imports remain compile-time types.
- Imported helper modules are allowed in the main dependency graph. Runtime variables declared in the function's surrounding module cannot be captured either; import shared main state from a main-only helper module.
- A marked function cannot rely on executable side effects in its declaring module. A module-level main file must be declarative: runtime exports are supported async functions. Side-effect imports, runtime re-exports, other runtime exports, and executable top-level statements are rejected.
- Use named async function declarations or async functions/arrows assigned to stable variables. Object/class methods, generators, and anonymous default exports are unsupported.
- Type-only exports and locally declared interfaces/type aliases are supported in main modules.
- Function IDs are generated by the compiler and registered in the generated manifest. Applications should not depend on their format.
- Directives must occur in the function body's directive prologue, before ordinary statements, or at the module top level for module-level marking.

Vite owns the client transform pipeline, including the app's framework transforms. Valence makes separate Vite build calls for the generated Electron main and preload output, with `configFile: false`; renderer framework plugins do not run on those privileged graphs. Electron and Node built-ins stay external and are supplied by Electron/Node at runtime.

## Current scope

Valence supports function- and module-level directives, typed async calls, generated main/preload wiring, structured-clone transport, and source diagnostics. It does not capture closures or support synchronous calls, streams, renderer event subscriptions, or server-side rendering. Keep route and UI code in the client graph and mark only privileged operations.

Put startup work, mutable state, and import-dependent policy in the configured lifecycle module. Use `valence/vite` for Vite integration, `valence/electron` for lifecycle helpers, and `valence/runtime/context` for per-invocation main context. Other runtime entry points implement Valence's generated bridge and dispatcher; ordinary application code should not import them to register functions, access IPC, or construct another bridge.

## Diagnostics

Compiler errors identify the author file and source location. Fix the source instead of substituting manual IPC:

| Code | Meaning | Typical correction |
| --- | --- | --- |
| `UM000` | Source cannot be parsed | Correct the JavaScript/TypeScript syntax. |
| `UM001` | Marked function is synchronous | Declare it `async` and await its callers. |
| `UM002` | Renderer/outer lexical dependency | Pass values as arguments; avoid browser globals and lexical `this`. |
| `UM003` | Function has no stable name | Use a named declaration or a function assigned to a variable. |
| `UM004` | Unsupported main-module export | Export supported async functions or types. |
| `UM005` | Duplicate generated identity | Resolve conflicting function identities reported by the compiler. |
| `UM006` | Module capture or type/value dependency cannot be extracted | Import a main-compatible helper or an explicit type; avoid surrounding runtime bindings. |
| `UM007` | Unsupported function form or module behavior | Follow the boundary rules; move startup into the lifecycle module. |
